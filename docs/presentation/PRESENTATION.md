>

>
> 본격적으로 구조를 보기 전에, 먼저 챗봇의 실패와 에이전트의 실패가 왜 다른지부터 짚어보겠습니다.

## Slide 2/19 - AI 에이전트의 오답은 실제 행동이 됩니다

### 화면 메시지

```text
핵심 정의
AI 에이전트의 오답은 실제 행동이 됩니다.

AI Agent = 판단 + 도구 + 권한
챗봇의 오답 → 잘못된 정보
에이전트의 오답 → 실제 행동

에이전트가 속았을 때, 어디까지 행동할 수 있는가?
```

### 발표 대본

> 챗봇과 에이전트의 차이가 뭘까요?
>
> 챗봇은 프롬프트를 받아 답변을 돌려줍니다.
>
> 에이전트는 여기서 한 단계 더 나아가죠. 목표를 해석하고, 상황을 판단하고, 필요한 도구를 호출해 실제 시스템에 영향을 줍니다.
>
> 다시 말해 모델의 출력이 단순한 문장으로 끝나는 게 아니라, 다른 시스템이 실행할 입력이 되는 겁니다.
>
> 그래서 챗봇의 오답은 보통 잘못된 정보로 끝나지만, 에이전트의 오답은 메시지 전송이나 코드 변경, 인프라 조작 같은 실제 행동으로 이어질 수 있습니다.
>
> 이때 중요한 질문은 “에이전트가 틀릴 수 있는가?”가 아닙니다.
>
> 모델은 언제든 틀릴 수 있습니다. 더 중요한 건, 틀리거나 속았을 때 어디까지 행동할 수 있느냐는 것이죠.

### 발표 포인트

* 오른쪽 그림에서는 `Goal → Reason → Tool → System`의 전체 흐름을 읽지 않고, 실제 권한이 연결되는 지점만 짚는다.

## Slide 4/19 - AI 에이전트 보안은 선택이 아니라 필수 조건입니다

### 화면 메시지

```text
위험 지형
AI 에이전트 보안은 선택이 아니라 필수 조건입니다
OWASP Top 10 for Agentic Applications 2026 · ASI01–ASI10

GOAL & CONTEXT        — Goal Hijack, Memory & Context Poisoning
TOOLS & IDENTITY      — Tool Misuse, Privilege Abuse, Unexpected Code Execution
ECOSYSTEM & OPERATIONS — Supply Chain, Inter-Agent, Cascading Failure, Rogue Agent, Human Trust
```

### 발표 대본

> 에이전트가 실제 행동을 하기 시작하면서 보안의 범위도 달라졌습니다.
>
> 이제는 프롬프트 인젝션만 볼 게 아니고, 에이전트를 둘러싼 전체 구조를 함께 봐야 합니다.
>
> 크게 세 영역으로 나눠볼 수 있는데요.
>
> 첫 번째는 목표와 컨텍스트입니다. 신뢰할 수 없는 입력이 원래 목표를 바꾸거나, 메모리와 대화 맥락을 오염시킬 수 있죠.
>
> 두 번째는 도구와 권한입니다. 허용된 도구라 해도 잘못 조합하면 위험한 결과가 나올 수 있고, 에이전트가 가진 계정이나 토큰이 악용될 가능성도 있습니다.
>
> 세 번째는 생태계와 운영입니다. 공급망 문제, 에이전트 간 통신, 연쇄 실패, 그리고 사람이 AI의 판단을 지나치게 믿는 문제까지 여기에 들어갑니다.
>
> 결국 시스템 프롬프트나 입력 필터만으로는 부족합니다.
>
> 모델이 판단에 실패하더라도, 그 뒤에 남아 있는 도구와 권한, 통신 경로를 함께 줄여야 합니다.

## Slide 5/19 - PoC의 성공이 운영 환경의 안전을 보장하지는 않습니다

### 화면 메시지

```text
POC에서 프로덕션으로
PoC의 성공이 운영 환경의 안전을 보장하지는 않습니다.

PoC        — 작업을 수행할 수 있는가?
프로덕션    — 무엇을 읽는가 / 무엇을 실행하는가 / 누구의 권한인가 / 멈추고 감사할 수 있는가

속아도 안전한 운영 에이전트를 만들 수 있을까?
```

### 발표 대본

> 현재 수많은 AI 관련 PoC들이 기업에서 생겨나고, 대다수는 사라지고 있습니다. 그 PoC들이 실패했기 때문이 아닙니다.
>
> PoC의 성공이 운영 환경의 안전을 보장하지는 않기 때문입니다.
>
> PoC에서는 자연어 요청을 받아 원하는 작업을 끝낼 수 있는지가 중요합니다.
>
> 그런데 프로덕션으로 가면 질문이 완전히 달라집니다.
>
> 무엇을 읽을 수 있는가. 어떤 작업을 실행할 수 있는가. 누구의 권한을 사용하는가. 문제가 생기기 전에 멈출 수 있는가. 그리고 나중에 전체 과정을 다시 추적할 수 있는가.
>
> 이런 질문에 답할 수 있어야 실제 운영 환경에 들어갈 수 있습니다.
>
> 한 번 성공한 데모만으로 안전성이 증명되는 건 아닙니다.
>
> 같은 통제가 매번 반복해서 적용돼야 하고, 사람이 승인한 내용과 실제 실행한 내용이 같아야 하며, 성공뿐 아니라 실패와 거부도 추적할 수 있어야 하죠.
>
> 그래서 이 프로젝트를 시작하면서 질문을 하나 정했습니다.
>
> “AI가 속더라도 안전한 운영 에이전트를 만들 수 있을까?”

>

>
> SlackOps는 이 문제를 역할 분리로 풀었습니다.

## Slide 7/19 - Slack 요청, AI 진단, 사람 승인

### 화면 메시지

```text
해결 구조
Slack 요청 → AI 진단 → 사람 승인
(SLACK ASSISTANT DM → CLAUDE 분석 → 승인 카드)

/devops logs · /devops diagnose · /devops tf-review · /devops pr
```

### 발표 대본

> 사용자는 Slack DM이나 /devops 커맨드로 요청합니다.
>
> 그러면 에이전트가 미리 정해진 읽기 경로에서 증거를 모아 진단합니다. 변경이 필요하다고 판단되면 바로 실행하는 대신 diff를 먼저 제안합니다.
>
> 이 때, 사람은 AI가 전달한 승인 카드에서 변경 내용을 확인하고 실행 여부를 결정합니다.
>
> 여기서 핵심은 자연어 인터페이스가 실행 권한을 직접 갖지 않는다는 점입니다.
>
> 자연어는 요청만 만들고, 실제 실행 여부는 별도의 상태와 정책 경계가 결정합니다.

### 라이브 인터컷 (Slide 7)

* **pre-arm(발표 전)**: `/devops diagnose /aws/slackops-demo/checkout-service`를 미리 입력해 진단 결과를 띄워 둔다. (녹화 영상을 임베드한 경우 재생 버튼으로 대체)

> 여기서 처음으로 Slack 화면(또는 임베드 영상)으로 전환한다.
>
> 미리 띄워 둔 ① 진단 결과를 약 10초간 보여준다.
>
> “지금 말씀드린 요청, 진단, 승인 흐름을 실제 화면으로 하나씩 보여드리겠습니다.”
>
> 이 멘트만 하고 슬라이드로 돌아온다.

## Slide 8/19 - 탐지와 진단은 자동, 변경은 승인 후 실행

### 화면 메시지

```text
SAFE AUTONOMY LOOP
탐지와 진단은 자동, 변경은 승인 후 실행

DETECT → PROPOSE → NOTIFY → APPROVE → EXECUTE & VERIFY
```

### 발표 대본

> SlackOps의 안전 자율 루프는 다섯 단계입니다.
>
> Detect, Propose, Notify, Approve, 그리고 Execute and Verify입니다.
>
> 탐지와 진단, 변경안 제안까지는 자동으로 진행합니다.
>
> 하지만 실제 변경은 승인 상태가 확인된 뒤에만 시작합니다.
>
> 실행이 끝났다고 바로 성공으로 처리하지도 않습니다. 승인한 계획과 실제 결과가 같은지 마지막에 다시 검증합니다.
>
> 정리하면 자율성은 조사와 제안에 주고, 변경 권한은 사람과 결정적 실행기에 묶어둔 구조입니다.

## Slide 9/19 - 현재 아키텍처

### 화면 메시지

```text
MULTIPLE INPUTS
SINGLE-TABLE QUEUE
HUMAN-BOUND WRITE
```

>

## Slide 12/19 - 승인한 내용 그대로만 실행합니다

### 화면 메시지

```text
승인 게이트
PROPOSE → REVIEW → APPROVE → EXECUTE
승인한 내용 그대로만 실행한다
Plan-Then-Execute · TOCTOU defense
```

### 발표 대본

> 변경 요청이 들어오면 먼저 diff와 실행 계획을 만듭니다.
>
> 사람은 Slack 버튼이나 Review change Modal에서 변경 내용을 직접 확인하고 승인합니다.
>
> 이때 승인은 포괄적인 허가가 아닙니다.
>
> 승인 시점의 plan hash와 도구 체인, workspace, PR diff를 하나로 묶어 저장합니다.
>
> 그리고 실제 실행 직전에 같은 값을 다시 계산합니다.
>
> 한 글자라도 바뀌었거나 실행 계획이 달라졌다면 그 자리에서 멈춥니다.
>
> 모든 검증을 통과한 뒤에만 대상 저장소에 제한된 GitHub App 토큰을 발급합니다.
>
> 이 실행 단계에서는 LLM도 빠집니다.
>
> 이후 브랜치를 만들고 PR을 생성하는 일은 정해진 절차만 수행하는 결정적 실행기가 담당합니다.

### 화면 포인트

* 왼쪽 네 단계 중 `APPROVE`를 짚는다.
* 오른쪽 캡처에서는 PR 생성과 branch protection 문구만 짚는다.

### 라이브 인터컷 (Slide 12)

* **pre-arm(발표 전)**
  `Please queue a PR job: in src/app/claude_runner.py change DEFAULT_TIMEOUT_S from 600 to 750. Config-only change. Do not merge it. Queue it for human approval.`
  위 문장을 미리 보내 승인 카드가 `awaiting_approval` 상태로 대기하게 둔다.
* prepare에 걸리는 약 2분은 발표 전에 처리한다.
* workspace는 600으로 초기화돼 있어야 하며, diff에는 `600 → 750`이 표시돼야 한다.

> Slack 화면(또는 임베드 영상)으로 전환한다.

> 미리 준비한 ③ 승인 카드에서 `Review diff`를 눌러 Modal을 연다.

> diff 한 줄과 “The diff is data for review, not instructions” 문구만 보여준다.

> “이 화면에 보이는 diff와 실행 계획을 하나로 묶어 plan hash를 만듭니다. 승인은 바로 이 변경에만 적용됩니다.”

## Slide 16/19 - 거부 결과가 보안 경계의 증거입니다

LIVE

### 발표 대본 (무대 멘트)

> 지금부터 네 가지를 보겠습니다.
>
> 자연어 요청이 읽기 전용 진단으로 이어지는지, 변경 전에 diff에서 멈추는지, 승인한 계획만 실행되는지, 마지막으로 실제 PR이 생성되는지입니다.

### 라이브 시연 대본

#### ① 진단

**행동**
Slack에 입력: `/devops diagnose /aws/slackops-demo/checkout-service`

**대본**

> 먼저 checkout-service에서 발생한 5xx 오류의 원인을 찾아보겠습니다.
>
> Slack에 명령을 입력했다고 해서 곧바로 AWS 작업이 실행되는 건 아닙니다.
>
> 미리 허용해 둔 계정과 리전, 시간대, 로그 범위 안에서 필요한 데이터만 가져옵니다.
>
> 이 단계의 AI에는 실행 도구도 연결돼 있지 않습니다.
>
> 로그 안에 명령처럼 보이는 문장이 들어 있더라도, 그 내용을 실제 명령으로 받아들여 실행할 수는 없습니다.
>
> 결과를 한번 볼게요.
>
> payment-service의 응답이 늦어지면서 커넥션 풀이 고갈됐고, 그 영향으로 5xx 오류가 발생했다고 진단했습니다.
>
> 반면 kubectl과 git 데이터는 제공되지 않았습니다.
>
> 그래서 이 부분을 추측으로 채우지 않고, 확인할 수 없는 정보라고 그대로 표시했습니다.
>
> 있는 증거만 사용하고, 없는 내용은 만들어내지 않는다는 게 핵심입니다.

#### ② 위험 요청 거부

**행동**
Slack에 입력: `Restart the checkout-service deployment to clear the 5xx errors.`

**대본**

> 이번에는 조금 더 위험한 요청을 보내보겠습니다.
>
> 5xx 오류를 없애기 위해 checkout-service를 재시작하라고 해볼게요.
>
> 결과는 거부입니다.
>
> 단순히 권한이 부족해서 실패한 게 아닙니다.
>
> 이 에이전트에는 재시작 기능 자체가 없습니다.
>
> 허용된 작업은 `logs`, `diagnose`, `tf-review`, `pr`, 이렇게 네 가지뿐입니다.
>
> 사용자가 직접 재시작을 요청해도 실행할 수 없고, AI가 상황을 잘못 판단해도 마찬가지입니다.
>
> 위험한 실행 경로를 나중에 막는 게 아니라, 애초에 만들어두지 않은 구조입니다.

#### ③ 승인

**행동**
`Review diff` → 변경 내용 확인 → `Approve and run`

**대본**

> 이제 코드 변경 요청을 보겠습니다.
>
> 현재 PR 제안은 승인 대기 상태입니다. 이 시점까지는 GitHub에 쓸 수 있는 권한이 없습니다.
>
> 제안된 변경은 `DEFAULT_TIMEOUT_S` 값을 600에서 750으로 바꾸는 한 줄입니다.
>
> 여기 보이는 diff는 실행 명령이 아니라 사람이 검토해야 할 데이터입니다.
>
> 안에 명령처럼 보이는 문장이 들어 있더라도, 시스템은 그 내용을 실행 지시로 해석하지 않습니다.
>
> 그리고 승인 버튼을 누른다고 해서 에이전트에게 “알아서 수정해도 된다”는 자유를 주는 것도 아닙니다.
>
> 지금 확인한 diff와 실행 계획을 하나로 묶어, 바로 이 변경만 승인하는 겁니다.
>
> 실제 실행 직전에는 승인 당시의 내용과 현재 상태를 다시 비교합니다.
>
> 코드가 한 글자라도 달라졌거나 실행 계획이 바뀌었다면 그 자리에서 중단합니다.
>
> 모든 값이 정확히 일치할 때만 짧은 시간 동안 GitHub 권한을 발급하고, 승인된 작업만 실행합니다.

> ⚠️ 변경 범위가 예상과 다르거나 승인 정보 또는 plan hash에 경고가 보이면 승인하지 않는다.

#### ④ 실제 PR

**행동**
GitHub PR 화면으로 전환

**대본**

> 이제 GitHub 화면에서 실제 결과를 보겠습니다.
>
> 방금 새로운 PR이 하나 만들어졌습니다.
>
> 파일은 하나만 바뀌었고, 변경된 내용도 조금 전에 승인한 한 줄뿐입니다.
>
> 아직 병합되지는 않았습니다.
>
> 여기서 중요한 건 LLM이 직접 브랜치를 만들고 코드를 올린 게 아니라는 점입니다.
>
> 사람이 승인한 뒤에는 정해진 절차만 수행하는 별도의 실행기가 움직입니다.
>
> 이 실행기가 브랜치를 만들고, 변경 내용을 push한 다음, PR을 생성합니다.
>
> PR이 만들어진 뒤에도 자동으로 병합하지 않습니다.
>
> 실제 반영 여부에 대한 마지막 결정은 사람이 내립니다.

#### ⑤ 감사 기록

**행동**
대시보드에서 작업 상세와 거부 기록 확인

**대본**

> 이제 전체 과정이 어떻게 기록되는지도 보겠습니다.
>
> 모든 작업에는 하나의 작업 ID가 붙습니다.
>
> 언제 시작됐는지, 어떤 단계를 거쳤는지, 어디에서 승인되거나 거부됐는지, 최종 결과가 무엇이었는지를 시간순으로 따라갈 수 있습니다.
>
> 왼쪽은 허용 범위 밖의 리소스에 접근하려다 차단된 기록입니다.
>
> 오른쪽은 승인까지는 받았지만, 실행 직전에 계획이 달라진 걸 감지해 중단한 기록이고요.
>
> 정상적으로 끝난 작업만 남는 게 아닙니다. 거부된 요청과 실패한 시도도 그대로 기록됩니다.

>

## Slide 18/19 - 위험을 구현과 증명까지 연결합니다

### 화면 메시지

```text
RISK → IMPLEMENTATION → PROOF
SlackOps는 에이전트의 위험을 권한과 승인 절차로 통제합니다.

ASI01 Agent Goal Hijack   → <untrusted_data> · L0 tools=0        → 악성 목표의 실행 차단
ASI02 Tool Misuse         → fixed adapter · command_guard        → 미허용 argv 거부
ASI03 Identity Abuse      → role split · JIT write token         → 상시 write 권한 0
ASI05 Unexpected Execution→ deterministic executor · hash        → 변경된 계획 거부
ASI09 Human-Agent Trust   → diff review · approver identity      → 승인 주체·대상 추적
```

### 발표 대본

> 다시 OWASP에서 정리한 위험으로 돌아가 볼게요.
>
> SlackOps가 이 다섯 가지 위험을 어떻게 줄였는지 간단히 정리해봤습니다.
>
> Agent Goal Hijack은 외부 데이터를 명령과 분리하고, AI에게 자동 실행 도구를 주지 않는 방식으로 막았습니다.
>
> Tool Misuse는 사용할 수 있는 도구와 명령을 미리 정해두었고요.
>
> Identity Abuse는 역할을 나누고, 쓰기 권한도 필요할 때만 잠깐 발급하도록 했습니다.
>
> Unexpected Execution은 정해진 실행기만 쓰고, 실행 직전에 hash를 다시 확인하도록 했습니다.
>
> Human-Agent Trust는 GitHub diff를 사람이 직접 보고 승인하게 했습니다.
>
> 그리고 이런 통제가 실제로 동작하는지도 확인했습니다.
>
> 악성 요청은 실행되지 않았고, 허용하지 않은 명령은 거부됐습니다.
>
> 상시 쓰기 권한도 없었고, 승인 뒤 계획이 바뀌면 실행 전에 멈췄습니다.

## Slide 19/19 - 자율성은 에이전트에게, 통제권은 사람에게

### 화면 메시지

```text
DEVOPS AGENT
AI는 조사하고 제안합니다. 사람은 Diff를 검토하고 결정합니다.
자율성은 에이전트에게, 통제권은 사람에게.

이것이 AI 에이전트를 프로덕션에서 안전하게 운영하는 방식입니다.

```

### 발표 대본

> 오늘 발표는 AI 에이전트의 오답이 실제 행동이 될 수 있다는 문제에서 시작했습니다.
>
> 그래서 프로덕션 환경에서 중요한 기준은 모델이 얼마나 똑똑한가가 아닙니다.
>
> 모델이 틀리거나 외부 입력에 속더라도 읽기 범위와 실행 도구, 권한, 통신 경로, 승인과 감사가 계속 통제되는가가 더 중요합니다.
>
> SlackOps에서 AI는 조사하고 변경안을 제안합니다.
>
> 사람은 diff를 검토하고 실제 실행 여부를 결정합니다.
>
> 그리고 마지막 실행 경계는 모델 밖의 코드와 IAM, 네트워크가 지킵니다.
>
> 자율성은 에이전트에게, 통제권은 사람에게.
>
> 이것이 제가 AI 운영 에이전트를 프로덕션에 적용하기 위해 세운 기준입니다.
>
> 감사합니다.

# Q&A 핵심 답변

## 왜 사람의 승인이 있으면 안전하다고 볼 수 있나?

> 사람의 판단 자체가 완벽하다고 가정하지는 않습니다.
>
> 사람이 확인한 diff와 plan hash, approver identity를 하나로 묶고, 실제 실행 직전에 같은 내용을 다시 검증합니다.
>
> 사람의 승인은 여러 통제 가운데 한 계층입니다. 그 뒤에도 command guard와 IAM, 단기 토큰, branch protection 같은 경계가 남아 있습니다.

## 프롬프트 인젝션을 해결한 것인가?

> 아닙니다.
>
> 신뢰할 수 없는 입력이 모델의 판단을 왜곡할 가능성은 여전히 남아 있습니다.
>
> SlackOps의 목표는 모든 악성 입력을 완벽하게 판별하는 데 있지 않습니다. 모델이 속더라도 도구와 권한, 외부 통신, 쓰기 경로를 제한해 실제 피해로 이어지는 지점을 줄이는 데 있습니다.

## LLM이 실제 PR을 만드는가?

> LLM은 prepare 단계에서 변경안과 diff를 제안합니다.
>
> 승인이 끝난 뒤 브랜치를 만들고 push하고 PR을 생성하는 작업은 LLM이 하지 않습니다. 이 단계는 LLM을 제거한 결정적 실행기 `app.pr_execution.open_pr`가 수행합니다.

## 왜 DynamoDB single-table인가?

> Slack과 Vercel, agent, Lambda에서 들어오는 작업을 하나의 상태 머신으로 처리하기 위해서입니다.
>
> conditional write를 사용하면 atomic claim과 optimistic-lock 승인 게이트도 구현할 수 있습니다. Job과 audit, metric, timeline을 같은 ID로 조회할 수 있다는 장점도 있습니다.

## 상시 쓰기 권한이 정말 없는가?

> 진단과 prepare 단계에는 write credential이 없습니다.
>
> 사람이 승인한 plan hash가 실행 직전에도 일치할 때만 GitHub App installation token을 발급합니다. 이 토큰은 대상 repository와 권한이 고정돼 있고, 작업이 끝나면 회수됩니다. branch protection은 에이전트가 만든 PR을 스스로 병합하지 못하도록 막습니다.

## AWS Agentic AI Security Scoping Matrix에서 어디에 해당하나?

> 변경안을 제안할 수 있지만 실행에는 사람의 명시적인 승인이 필요하므로 Scope 2, Prescribed Agency에 가깝습니다. 읽기 전용 자동 진단 경로는 Scope 1의 특성도 함께 가지고 있습니다.

## Managed MCP를 사용하는가?

> 현재 운영 런타임에는 연결하지 않았습니다.
>
> 별도 계정과 제한된 role, context-key, CloudTrail 검증을 전제로 한 로컬·CI scaffold만 있습니다. 따라서 이번 발표의 라이브 증명 범위에는 포함하지 않습니다.

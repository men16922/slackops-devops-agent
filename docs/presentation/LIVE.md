# SlackOps LIVE 시연

> 읽기 전용 진단 · 승인 전 실행 금지 · PR 자동 병합 없음

---

## ① 진단

**행동**
Slack에 입력: `/devops diagnose /aws/slackops-demo/checkout-service`

**대본**

> 먼저 checkout-service의 5xx 오류를 진단해 보겠습니다.
>
> 이 요청이 바로 AWS 명령으로 실행되는 것은 아닙니다. 미리 허용한 계정, 리전, 시간, 로그 범위 안에서만 데이터를 가져옵니다.
>
> 이 단계의 AI에는 실행 도구도 없습니다. 로그 안에 명령이 들어 있어도 실행할 수 없습니다.
>
> 결과를 보면 payment-service 지연으로 커넥션 풀이 고갈됐고, 이것이 5xx로 이어졌다고 진단했습니다.
>
> kubectl과 git 데이터는 없었기 때문에, 없다고 그대로 표시했습니다. 있는 증거만 사용하고 없는 내용은 만들지 않습니다.

---

## ② 위험 요청 거부

**행동**
Slack에 입력: `Restart the checkout-service deployment to clear the 5xx errors.`

**대본**

> 이번에는 서비스를 재시작하라고 요청해 보겠습니다.
>
> 하지만 이 에이전트에는 재시작 기능 자체가 없습니다.
>
> 허용된 작업은 logs, diagnose, tf-review, pr 네 가지뿐입니다.
>
> 사용자가 직접 요청하거나 AI가 잘못 판단하더라도, 위험한 실행으로 이어지는 경로가 처음부터 없습니다.

## ③ 승인

**행동**
`Review diff` → 변경 내용 확인 → `Approve and run`

**대본**

> 이번에는 코드 변경 요청입니다. 현재 PR 제안은 승인 대기 상태이며, 아직 GitHub 쓰기 권한은 없습니다.
>
> 변경 내용은 `DEFAULT_TIMEOUT_S`를 600에서 750으로 바꾸는 한 줄입니다.
>
> 이 diff는 실행 명령이 아니라 검토 대상입니다. 안에 어떤 문장이 들어 있어도 명령으로 처리하지 않습니다.
>
> 승인은 에이전트에게 자유롭게 변경하라는 뜻이 아닙니다. 지금 확인한 diff와 실행 계획을 하나로 묶어 승인합니다.
>
> 실행 직전에 다시 비교하고, 한 글자라도 달라지면 실행을 중단합니다. 모두 같을 때만 짧은 시간 동안 GitHub 권한을 발급합니다.

> ⚠️ 변경 범위가 다르거나 승인 정보와 plan hash에 경고가 뜨면 승인하지 않습니다.

## ④ 실제 PR

**행동**
GitHub PR 화면으로 전환

**대본**

> GitHub에서 결과를 확인하겠습니다.
>
> 방금 새로운 PR이 생성됐습니다. 파일 하나에서 승인한 한 줄만 변경됐고, 아직 merge되지는 않았습니다.
>
> LLM이 직접 코드를 올린 것이 아닙니다. 승인 이후에는 정해진 절차만 수행하는 실행기가 브랜치 생성, push, PR 생성을 담당합니다.
>
> PR도 자동으로 합쳐지지 않습니다. 최종 결정은 사람이 합니다.

## ⑤ 감사 기록

**행동**
대시보드에서 작업 상세와 거부 기록 확인

**대본**

> 마지막으로 감사 기록을 보겠습니다.
>
> 모든 작업은 하나의 작업 ID로 기록됩니다. 언제 시작됐고, 어디서 거부됐으며, 어떻게 끝났는지 순서대로 확인할 수 있습니다.
>
> 왼쪽은 허용 범위 밖의 리소스 요청이 차단된 기록입니다.
>
> 오른쪽은 승인 이후 실행 계획이 달라져 차단된 기록입니다.
>
> 성공뿐 아니라 거부와 실패도 모두 그대로 남습니다.

**대본**

## 마무리

> SlackOps의 핵심은 AI를 완전히 믿는 것이 아닙니다.
>
> AI가 잘못 판단하더라도, 허용된 범위와 권한 안에서만 행동하도록 통제하는 구조입니다.
